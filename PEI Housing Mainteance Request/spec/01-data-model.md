# Data Model

**Status:** Draft v0.3 · Companion to `00-requirements.md`

> **v0.2:** Vendor removed as an entity and as an assignee. Outside work is recorded as a
> text reference on cost lines, not managed as a system actor.
> **v0.3:** coordinator team is 2 — routing is load-based, not market-based. Resident intake
> fields added to Ticket; see `05-resident-intake.md` §7 for the full list and rationale.

---

## Entity overview

```
Property ──< Unit ──< Occupancy >── Person
                │                      │
                └──< Ticket >──────────┘
                      │  ├──< Task ──> Person        ← the assignable work
                      │  ├──< TicketComment
                      │  ├──< Attachment
                      │  ├──< CostEntry
                      │  └──< AuditEvent
Lease ──> Unit, Landlord
Asset ──> Unit   (for preventive maintenance)
TaskTemplate ──< TaskTemplateStep      ← automation reads these to generate Tasks
```

Design rules:

- **Ticket is the only object users create directly.** Everything else is either reference
  data a ticket points at, or generated by automation.
- **Task is the only object users are assigned.** A dashboard of tickets tells you what
  exists; a list of tasks tells you what to do.

## Task — the assignable work

A ticket is the *request*; tasks are the *work*. Automation generates tasks from templates
and routes each to a PEI owner. A ticket cannot resolve while a required task is open.

| Field | Type | Notes |
|---|---|---|
| task_id | PK | |
| ticket_id | FK | |
| template_task_key | text, nullable | Which template step produced it — lets reporting compare the same step across tickets |
| sequence | int | Display and dependency order |
| name | text | "Confirm move-out date with occupant" |
| instructions | text, nullable | Shown to the assignee |
| assigned_to_id | FK → Person | Always a PEI person |
| assignment_rule | text, nullable | How it was auto-assigned — e.g. `owner_coordinator`, `coordinator_by_load` |
| status | enum | `not_started`, `blocked`, `in_progress`, `done`, `skipped` |
| required | bool | If true, blocks ticket resolution |
| blocked_by_task_id | FK, nullable | Stays `blocked` until the predecessor is `done` |
| due_at | ts | Computed from template offset |
| completed_by / completed_at | FK / ts | |
| skip_reason | text | **Required** to set status `skipped` |
| evidence_required | enum, nullable | `photo`, `document`, `none` — blocks `done` until an attachment of that kind exists |
| external_party | text, nullable | Free text naming the outside company doing the work, when relevant. A note, not a relationship — the PEI assignee still owns the task. |

## CostEntry

Separate rows rather than one cost field, so labor, parts, and multiple invoices on one
ticket stay distinguishable and auditable.

| Field | Type | Notes |
|---|---|---|
| cost_id | PK | |
| ticket_id | FK | |
| payee_name | text | Free text — the company or person invoiced. Not a managed entity. |
| cost_type | enum | `labor`, `parts`, `trip_charge`, `permit`, `disposal`, `other` |
| amount | money | |
| invoice_number / invoice_date | text / date, nullable | |
| approval_status | enum | `pending`, `approved`, `rejected` |
| approved_by / approved_at | FK / ts | |
| chargeable_to | enum | Defaults from ticket, overridable per line |

> `payee_name` as free text is deliberate. It preserves cost reporting without reintroducing
> vendor management. If spend-by-payee reporting later matters, normalize it then — a
> lookup list is a cheap change; a vendor module is not.
